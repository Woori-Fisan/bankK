# 은행 백엔드 서버

은행의 여러 원장 데이터베이스를 관리하고 은행의 업무를 BaaS 형태의 API로 제공하는 서버입니다.

## 1. 기술 스택

| 구분 | 기술 | 비고 |
|------|------|------|
| DB | MySQL 8.4 | 기본 격리수준(REPEATABLE READ) 기반 + 비관적 락 사용 |
| 배치 | Spring Batch 6.0.3 | RSA 키 재발급 |
| 캐시 | Redis | 멱등성 키 저장 전용 (TTL 1분) |

## 2. 트랜잭션 처리
원장 데이터베이스에 대해 삽입, 삭제, 수정의 작업을 요구하는 요청을 처리할 때, 해당 과정은 트랜잭션으로 취급되어야 합니다.
트랜잭션이 가지는 ACID 특성을 지켜서, 작업의 원자성과 일관성을 보장해야 합니다. 실패 시 롤백한다.

### 2.1. 동시성 제어 (Pessimistic Lock)
동일 계좌에 동시 출금·이체 요청이 들어올 경우 **갱신 손실(Lost Update)** 과 **마이너스 잔액** 이 발생하지 않도록 **비관적 락**을 사용합니다.

## 3. 멱등성 보장 (Idempotency)
네트워크 지연이나 타임아웃으로 인해 플랫폼이 동일한 이체/출금 요청을 재시도하더라도, 중복 결제가 발생하지 않도록 고유 트랜잭션 ID를 통해 멱등성을 보장해야 한다.
멱등키의 경우 Redis에 저장하여 일정시간(1분) 동안 유지한다.
만약 동일한 키가 입력되었을 경우 마지막 요청을 기준으로 TTL을 갱신한다.
멱등성 키 수신: 클라이언트가 `X-Idempotency-Key` 헤더에 UUID를 담아 전송하며, Filter 계층에서 헤더를 파싱하여 Redis 중복 여부를 검증합니다.

### 3.1. 처리 흐름

```
요청 수신 (idempotencyKey 포함)
    ↓
Redis에서 idempotencyKey 존재 여부 조회
    ↓ (이미 존재)              ↓ (신규)
기존 처리 결과 그대로 반환    실제 트랜잭션 처리
    ↓                         ↓
TTL 1분 재시작              결과 + idempotencyKey Redis 저장 (TTL 1분)
                              ↓
                           응답 반환
```

## 4. BaaS API
- **공통기능**: 요청이 들어왔을 때 최우선 실행되는 인증 처리
    - JWS 서명 검증 -> E2EE 복호화
- **계좌 조회**: 단일 계좌 정보 및 잔액 확인
    - 동작 흐름: (계좌/본인 권한 검증 -> 원장 조회 -> 반환)
- **거래 내역 조회**: 단일 계좌의 거래 내역 조회
    - 동작 흐름: (계좌/본인 권한 검증 -> 원장 조회 -> 반환)
- **이체**:
    - 이체 처리: (수취인 확인 -> 출금 원장 차감 -> 입금 원장 증액 -> 트랜잭션 기록 -> 반환)
- **수취인 확인**:
    - 입금 계좌 수취인명 확인
    - 수취인 확인: (입금 대상 계좌 유효성 및 예금주 식별 정보 확인 -> 반환)
- **출금**:
    - 출금 처리: (출금 원장 차감 -> 트랜잭션 기록 -> 반환)
- **대출 심사**: (요청 수신 -> E2EE 복호화 -> 신청자 정보 확인 -> CSS 신용 심사(모킹) -> 가승인 한도/금리 반환)
    - CSS 신용 심사는 비동기로 처리된다.
- **대출 진행**: (서류 해시값 전달 및 무결성 확인 -> 대출 최종 승인 -> 대출 원장 생성 및 입금 -> 트랜잭션 기록 -> 반환)
- **필요 서류 조회**: (요청 수신 -> 대출 서류 전달)
- **RSA 공개키 조회**: (요청 수신 -> RSA 공개키 반환)

## 5. mTLS
BaaS로 제공되는 API와의 통신은 FAPI 표준을 준수하기 위해 mTLS를 활용합니다.
mTLS는 상호 인증서 방식의 통신으로, 서로의 인증서 정보를 확인하여 중간자 공격에 대처하기 위한 방법입니다.
미리 발급받은 인증서를 통해 플랫폼 측과 mTLS 연결을 수행하도록 해야합니다.
은행 코어는 서버(Server) 역할로서, 플랫폼으로부터 인입되는 모든 요청에 대해 사전에 등록된 플랫폼의 클라이언트 인증서 정보를 확인합니다. 이를 통해 인가되지 않은 외부망의 접근 및 중간자 공격을 원천 차단합니다.

## 6. 보안 및 암호화

### 6.1. 암호화 알고리즘 용도 구분

| 알고리즘 | 용도 | 금지 사항 |
|----------|------|-----------|
| **AES-256-GCM** | DB 저장: 주민번호, 전체 계좌번호 | ECB 모드 금지 |
| **SHA-256** | 고정 Salt 값 추가, Blind Index 생성, 파일 무결성 검증 | 비밀번호 단방향 해시에 사용 금지 |
| **RSA-2048** | 중계 플랫폼으로부터 수신한 E2EE 데이터 복호화 | |
| **bcrypt** | 계좌 비밀번호 DB 저장 | SHA-256으로 대체 금지 |

### 6.2. AES-256-GCM (DB 저장 암호화)
- AES-256-GCM 저장 방식 상세: IV는 매 암호화마다 랜덤 생성, 암호문과 함께 저장
- IV + CipherText + AuthTag를 하나의 컬럼에 합쳐서 저장

### 6.3. 블라인드 인덱스 (Blind Index)
AES-GCM은 IV가 랜덤이므로 동일 계좌번호도 매번 다른 암호문 생성 → `WHERE` 절 직접 검색 불가.
`SHA-256(고정Salt + 계좌번호)` 해시값을 별도 컬럼(`account_no_hash`)으로 관리하여 검색합니다.

```
[계좌번호 검색 흐름]
입력값 → SHA-256(고정Salt + 계좌번호) → account_no_hash WHERE 조회
                                              ↓
                                    account_no_enc AES 복호화 → 마스킹 → 화면 출력
```

* 블라인드 인덱스용 고정 Salt는 **환경변수**로만 관리합니다. DB나 코드에 노출 금지.

### 6.4. 디지털 봉투 해독 (RSA + AES Decryption)
중계 플랫폼은 내용을 볼 수 없도록 디지털 봉투 방식의 종단 간 암호화(E2EE)가 적용된 요청을 전달합니다.
은행 코어 백엔드는 안전하게 보관된 **은행의 RSA 개인키**를 사용하여 프론트엔드가 보낸 '1회용 AES 세션 키'와 '비밀번호 (bcrypt)'를 우선 복호화합니다.
그 후, 획득한 1회용 AES 세션 키를 사용하여 계좌번호, 금액 등의 대용량 페이로드를 최종 복호화하여 원장 처리를 수행합니다.

### 6.5. DB 저장 암호화
DB에 고객의 개인 정보를 저장할 때, 은행 자체의 AES 키를 활용하여 암호화 과정을 거치며 컬럼(`account_no_enc`)에 저장.
데이터를 조회하는 과정을 위해 `SHA-256(고정Salt + 계좌번호 평문)` 해시값을 저장할 별도 컬럼(`account_no_hash`)를 생성한다(6.3. 블라인드 인덱스 (Blind Index) 적용).

## 7. JWS 서명 검증
중계 플랫폼이 첨부한 JWS 전자서명을 검증하여 요청 위변조 여부를 확인합니다.
중계 플랫폼의 공개키를 활용하여 서명을 검증하며, 위변조가 감지되거나 서명이 누락된 경우 즉시 예외를 발생시키고 거래를 중단합니다.

```
[JWS 검증 흐름]
요청 수신 (Request body: JWS-Signature)
    ↓
JwsVerificationFilter: 플랫폼 공개키로 서명 검증
    ↓ (검증 실패)           ↓ (검증 성공)
즉시 거절 + 보안 로그 기록  트랜잭션 처리 진행
```

## 8. RSA 키 교체 정책 (Key Rotation)
* **교체 주기**: Spring Batch `RsaKeyRotationJob`을 매일 새벽 2시에 스케줄링하여 RSA-2048 키페어를 자동 생성·교체합니다.
* **Job 구성**: `KeyPairGenerateStep` → `KeyStoreSaveStep` → `OldKeyDeprecateStep` 3단계로 구성합니다.
* **키 저장**: 생성된 키는 환경변수로 주입합니다. 키 파일을 코드·Git에 포함하는 것을 절대 금지합니다.
* **구 키 병행 유지**: 교체 직후 1시간 동안 구 키를 유지하여 플랫폼의 공개키 갱신 시간을 확보합니다. 복호화 시 신 키 실패 시 구 키로 폴백합니다.
